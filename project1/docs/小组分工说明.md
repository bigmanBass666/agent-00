## 二、技术栈选择及理由

### 2.1 最终选型

| 环节 | 选择 | 说明 |
|------|------|------|
| 教材 | The Anabolic Cookbook 2.0（205 页） | 章节结构清晰（209 条书签），满足"≥100 页 + 清晰章节"要求 |
| 文本提取 | PyMuPDF | 保留页码，支持书签（TOC）读取 |
| 分块 | 章节优先 + 3500 字符兜底 | 菜谱书"一菜一章"，按章节切保证配料与步骤不被割裂 |
| 检索 | 自研 numpy 余弦 + IDF 词汇召回（双路） | 方案 C 变体：不引入框架，直接调 API，理解最深入 |
| 精排 | bge-reranker-v2-m3 | 交叉编码器二次排序 |
| 生成 | Qwen3-8B（SiliconFlow） | 免费层、中文稳定、关闭 thinking 保证可控 |

### 2.2 为什么不用参考方案 A（DSH + FTS5）

1. **差异化要求**：v2 明确鼓励选择与参考案例不同的技术栈，非方案 A 且实现完整可在"技术选型与多样性"项获满分。
2. **检索质量**：菜谱书存在大量口语化提问（"how do I make…""what's in…"），FTS5 关键词匹配对同义表达不敏感；向量检索 + 交叉编码器重排能覆盖语义相近表述。
3. **可解释性**：自研管线每一层（召回/重排/拒答）都能单独打印中间结果，便于定位失败原因（本项目的三轮迭代正是靠这一点定位到 context 截断 bug）。

### 2.3 归类说明

本实现属于 **方案 C（直接调用 LLM API + 自定义检索逻辑）的变体**：知识库未使用 SQLite FTS5，而是以 `kb_chunks.json` + `kb_vectors.npy` 落地，检索用 numpy 暴力余弦（159 块规模下毫秒级）。未引入 LangChain 等框架，理由是数据规模小、链路短，框架带来的抽象成本大于收益。

## 四、协作机制

1. **每周一次组会**：对照看板（To do / Doing / Done）过进度，会议纪要提交至 `minutes/`
2. **提测即留痕**：任何指标改动必须留 A/B 记录（同一评测集、改动点、前后对比）
3. **问题不隐瞒**：发现系统越界输出（如幻觉、误答）当场记录并计入失败案例，不回避
4. **答辩共担**：组长主讲实现与设计；其余成员对各自"参与讨论 + 成果确认"的内容如实说明，实现部分如实告知"AI 辅助完成"；评审前完成组内彩排
